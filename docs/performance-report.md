# รายงานประสิทธิภาพในเครื่อง

วัดเมื่อ 2026-10-04 หลังเพิ่มปฏิทินรายเดือน โดยยังใช้ migration รุ่น 6 ด้วย `npm run performance` สคริปต์สร้าง SQLite ชั่วคราว 5,000 รายการ (ทุกลำดับที่ 20 มีกำหนดส่งในเดือนตุลาคมและตั้งเตือนล่วงหน้า 7 วัน) เปิด Express บนพอร์ตสุ่ม และเรียกผ่าน HTTP loopback หลัง warm-up 1 ครั้ง สถานการณ์ละ 20 requests ขนาดหน้ารายการคงที่ 20, ศูนย์เตือนสูงสุด 50 รายการ และปฏิทินสูงสุด 500 รายการ

## สภาพแวดล้อม

- Windows `win32 x64`
- Node.js `v24.18.0`
- SQLite จาก `node:sqlite`
- เครื่อง local ใน workspace นี้; ไม่มี network ภายนอกในเส้นทางที่วัด

## ผลที่วัดได้

| สถานการณ์ | ต่ำสุด | Median | P95 | สูงสุด |
| --- | ---: | ---: | ---: | ---: |
| รายการหน้าแรก เรียงล่าสุด | 2.53 ms | 14.65 ms | 17.94 ms | 18.23 ms |
| ค้นหาชื่อและกรอง `DONE` พร้อมกัน | 2.24 ms | 14.51 ms | 17.93 ms | 19.18 ms |
| ศูนย์เตือนที่ถึงช่วงแล้ว | 2.50 ms | 14.37 ms | 17.64 ms | 21.76 ms |
| ปฏิทินเดือนตุลาคม (250 งาน) | 4.59 ms | 13.93 ms | 21.51 ms | 24.48 ms |

API ใช้ `LIMIT 20 OFFSET ...` จึงแบ่งหน้าที่ backend และโหลด tags/subtasks ด้วย batch query แยกอย่างละหนึ่งครั้งแทน N+1 query ศูนย์เตือนใช้ partial index เฉพาะงานที่ยังไม่เสร็จและเปิดเตือน แล้วจำกัด 50 รายการ ปฏิทิน query ช่วง `due_date >= ต้นเดือน AND due_date < ต้นเดือนถัดไป` ผ่าน index วันครบกำหนดเดิม จำกัด 500 งาน และ batch-load ข้อมูลสัมพันธ์เช่นกัน การค้นหา substring แบบ `%term%` ต้อง scan ชื่อบางส่วน; ที่ขนาดข้อมูลเป้าหมายยังไม่พบเหตุให้เพิ่ม cache หรือ search engine

ผลนี้ยืนยันเฉพาะ workload ผู้ใช้คนเดียวและ environment ข้างต้น ไม่ใช่หลักฐานรองรับผู้ใช้พร้อมกันจำนวนมากหรือ production traffic
